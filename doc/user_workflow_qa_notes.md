# HRNS-NOW 사용자 흐름 QA 메모

이 문서는 다음 UI/UX 개선 Phase를 정하기 전에 사용자가 실제 화면을 보며 의견을 남기는 작업 공간입니다.

- 정책과 Harness 계약을 확정하는 문서는 아닙니다.
- `WORKFLOW_STATE.json`의 기계적 상태가 작업 가능 여부를 결정한다는 원칙은 유지합니다.
- 각 항목의 `사용자 메모` 아래에 불편한 점, 원하는 문구, 우선순위, 예외 상황을 자유롭게 추가합니다.
- 화면에 없는 동작은 `현재 상태`에 분명히 적고, 원하는 위치와 조건을 함께 기록합니다.

## 현재 확인된 QA 메모

- `Q1. 기본 경로에서 진단 후 등록이 완료되지 않는 문제`
  - 화면 위치: 왼쪽 사이드바 `프로젝트 관리` → 프로젝트 등록 폼 또는 `프로젝트 등록` 팝업의 맨 아래 `진단 후 등록` 버튼
  - 관찰: 기본 설정으로는 등록이 되지 않는 것처럼 보이며, `고급 설정`에서 외부 프로젝트 경로를 지정하면 등록됩니다.
  - 확인할 점: 실패 원인이 팝업 안에서 즉시 보이는지, 개발용 내장 SDK가 없을 때 다음 행동이 명확한지
  - 사용자 메모:
    -

- `Q2. 오늘 계획이 없을 때 시작 흐름이 보이지 않는 문제`
  - 화면 위치: 왼쪽 사이드바 `작업 계획` → 상단 `요구사항 작성` 카드, 하단 `실행 작업` 카드
  - 관찰: 오늘 날짜의 계획이 없는데 이전 날짜의 `개발 전략`이 보이면 요구사항 작성이 활성화되지 않는 것처럼 보입니다. 또한 오늘 작업을 시작하는 버튼이 화면에 없습니다.
  - 확인할 점: 과거 Markdown 내용과 오늘의 `WORKFLOW_STATE.json` 상태를 구분해 안내하는지, 오늘 시작 조건을 어떤 정책으로 열지
  - 사용자 메모:
    -

- `Q3. 버튼의 상태 피드백 부족`
  - 화면 위치: 전체 화면의 버튼, 특히 `진단 후 등록`, `요구사항 저장`, `환경 점검 실행`, `실행 작업` 카드의 작업 버튼
  - 관찰: hover 시 포인터·색상 변화와 클릭 뒤 진행 중 표시가 일관되지 않아 실행 여부를 판단하기 어렵습니다.
  - 확인할 점: 클릭 가능/불가, 진행 중, 성공, 실패 상태가 버튼과 인접한 결과 영역에 모두 드러나는지
  - 사용자 메모:
    -

- `Q4. 영문 글꼴과 혼합 표기 품질`
  - 화면 위치: 전체 화면, 특히 영문 제목·상태 코드·경로·명령 관련 텍스트
  - 관찰: 한글은 자연스럽지만 영문은 다소 어색하거나 깨져 보입니다.
  - 확인할 점: 일반 영문에는 자연스러운 sans-serif를 쓰고, 경로·코드·명령처럼 정렬이 중요한 곳에만 고정폭 글꼴을 쓰는지
  - 사용자 메모:

## 사용자가 따라가는 권장 흐름

- `0. 앱을 열고 현재 연결 상태를 파악한다`
  - 화면 위치: 모든 화면의 상단 활성 프로젝트 리본, 왼쪽 사이드바
  - 현재 화면에서 보이는 것:
    - 상단 리본에 활성 프로젝트 이름과 상태가 표시됩니다.
    - 왼쪽 사이드바에서 `프로젝트 관리`, `작업 현황`, `작업 계획`, `실행 기록`, `복구 센터 · 마감 확인`으로 이동합니다.
  - 사용자가 확인할 것:
    - 지금 어떤 프로젝트가 활성 상태인지 즉시 알 수 있는가
    - 프로젝트가 없거나 연결이 깨졌을 때 첫 이동 위치가 자연스러운가
  - 사용자 메모:
    -

- `1. 개발 SDK 또는 외부 Harness Kit을 준비하고 프로젝트 연결 화면으로 간다`
  - 화면 위치: 왼쪽 사이드바 `프로젝트 관리` → 화면 상단 `프로젝트 관리` 카드
  - 현재 화면에서 보이는 것:
    - 등록 프로젝트가 없으면 프로젝트 연결 입력 폼이 카드 안에 바로 나타납니다.
    - 이미 등록한 프로젝트가 있으면 카드의 `프로젝트 등록` 버튼을 눌러 팝업을 엽니다.
    - 기본 경로는 개발용 내장 SDK를 사용하도록 설계되어 있습니다.
    - `고급 설정`을 열면 `외부 Harness Kit 사용`을 선택하고 Kit 경로를 직접 지정할 수 있습니다.
  - 사용자가 해야 할 것:
    - 기본 개발 SDK를 쓸지, 외부 Kit을 명시적으로 연결할지 선택합니다.
  - 정책상 중요한 점:
    - 외부 Kit으로 자동 전환하면 안 됩니다. 내장 SDK가 없거나 사용할 수 없으면 이유와 다음 선택지를 분명히 보여야 합니다.
  - 사용자 메모:
    -

- `2. 프로젝트·작업공간·저장소를 연결하고 환경 점검 후 등록한다`
  - 화면 위치: `프로젝트 관리` → 프로젝트 연결 입력 폼 또는 `프로젝트 등록` 팝업
  - 현재 화면의 입력 위치:
    - 상단: `표시명`
    - 그 아래: `Workspace root`(작업공간 경로)
    - 그 아래: `Repository root`(대상 프로젝트 저장소 경로)
    - 그 아래: `Profile`
    - 하단: `고급 설정`과 `진단 후 등록` 버튼
  - 사용자가 해야 할 것:
    - 작업공간과 대상 저장소를 서로 다른 외부 경로로 지정합니다.
    - `진단 후 등록`을 누르고, 경계 검사·환경 점검·호환성 검사 결과를 확인한 뒤 등록합니다.
  - 기대 결과:
    - 진행 중에는 버튼이 로딩 상태가 됩니다.
    - 성공하면 등록된 프로젝트가 활성 프로젝트로 명확히 표시됩니다.
    - 실패하면 어떤 경로·SDK·검사가 막았는지 팝업 안에서 바로 이해할 수 있어야 합니다.
  - 사용자 메모:
    -

- `3. 활성 프로젝트와 작업 날짜를 확인한다`
  - 화면 위치: `프로젝트 관리` → 프로젝트 관리 카드 아래 `작업 날짜` 카드
  - 현재 화면에서 보이는 것:
    - 등록된 프로젝트의 요약과 활성 상태가 보입니다.
    - 작업 날짜 카드에는 작업공간에서 발견한 날짜별 폴더가 표시됩니다.
    - 과거 날짜를 선택하면 읽기 전용으로 표시됩니다.
  - 사용자가 해야 할 것:
    - 작업하려는 날짜가 오늘인지, 과거 기록을 보는 중인지 확인합니다.
  - 개선 판단이 필요한 점:
    - 오늘 날짜 폴더나 State가 아직 없을 때, 사용자가 다음에 `오늘 작업 시작`을 눌러야 한다는 안내가 현재 충분히 보이지 않습니다.
  - 사용자 메모:
    -

- `4. 오늘 작업을 시작할 준비를 한다`
  - 화면 위치: 현재는 명확한 시작 진입점이 부족합니다. 후보 위치는 `작업 현황` 화면의 `다음 작업` 카드이며, `작업 계획` 하단 `실행 작업` 카드에도 같은 행동을 보조로 둘 수 있습니다.
  - 현재 상태:
    - 오늘 날짜의 State가 아직 없을 때 사용자가 눌러야 할 명시적 `오늘 작업 시작` 버튼이 없습니다.
  - 사용자가 기대할 흐름:
    - 오늘 날짜인지, 프로젝트 연결과 환경 점검이 통과했는지 확인합니다.
    - 조건이 맞으면 `오늘 작업 시작`을 선택합니다.
    - 앱은 Harness의 정식 typed command만 실행하고, 종료 뒤 `WORKFLOW_STATE.json`을 다시 읽습니다.
  - 정책상 중요한 점:
    - 이전 날짜의 `TODAY_STRATEGY.md` 내용이 보인다는 이유만으로 오늘 작업이 이미 시작됐다고 판단하면 안 됩니다.
    - 이 시작 행동을 어느 State·날짜·잠금 조건에서 열지 먼저 결정해야 합니다.
  - 사용자 메모:
    -

- `5. 요구사항을 작성한다`
  - 화면 위치: 왼쪽 사이드바 `작업 계획` → 화면 최상단 `요구사항 작성` 카드 → `요구사항 작성` 버튼
  - 현재 화면에서 보이는 것:
    - 버튼을 누르면 `REQUEST_INBOX.md` 내용을 작성하는 팝업이 열립니다.
    - 팝업 하단에서 저장 가능 여부와 저장 불가 사유를 확인하고 저장합니다.
  - 사용자가 해야 할 것:
    - 오늘 시작 뒤 State가 요구사항 입력을 허용하는 경우에만 요구사항을 작성하고 저장합니다.
  - 기대 결과:
    - 저장 성공 시 팝업이 닫히고, 다음 가능한 작업이 갱신됩니다.
    - 저장할 수 없는 상태라면 단순 비활성화가 아니라 이유와 다음 행동이 보입니다.
  - 정책상 중요한 점:
    - 버튼 활성화는 `TODAY_STRATEGY.md`가 존재하는지 아닌지가 아니라 State와 날짜·잠금 정책에 따라야 합니다.
  - 사용자 메모:
    -

- `6. 작업 계획을 만들고 확인한다`
  - 화면 위치: `작업 계획` 화면 → 요구사항 작성 카드 아래
  - 현재 화면에서 보이는 것:
    - `개발 전략`: 사람이 읽는 `TODAY_STRATEGY.md` 내용
    - `작업 대기열`: 기계가 판단하는 queue와 현재 실행 대상
    - `실행 확인`: 실행 전 알아야 할 상태·제약
    - 화면 하단 `실행 작업`: 지금 허용된 단일 행동을 실행하는 영역
  - 사용자가 해야 할 것:
    - 요구사항 저장 후 허용될 때 `작업 준비` 또는 계획 생성 행동을 실행합니다.
    - 계획 생성 뒤 State와 작업 대기열을 다시 확인합니다.
  - 정책상 중요한 점:
    - 개발 전략은 설명용 화면이고, 실제 실행 가능 여부는 State와 Action Policy가 결정합니다.
  - 사용자 메모:
    -

- `7. 허용된 단일 작업을 실행한다`
  - 화면 위치: `작업 현황` → `다음 작업` 카드, 또는 `작업 계획` → 하단 `실행 작업` 카드
  - 현재 화면에서 보이는 것:
    - 지금 정책이 권장하는 단일 code/doc 실행 행동과 실행 전 확인 정보가 표시됩니다.
    - 실행 전에는 wrapper, target, scope, validation, compatibility, lock 정보를 읽기 전용으로 확인합니다.
  - 사용자가 해야 할 것:
    - 허용된 하나의 작업만 선택해 실행하고, 완료 뒤 새 State를 확인합니다.
  - 기대 결과:
    - 누른 버튼은 진행 중임을 나타내고 중복 실행을 막습니다.
    - 성공·실패를 stdout 문구만으로 결정하지 않고 State 재조회 결과로 보여 줍니다.
  - 사용자 메모:
    -

- `8. 실행 결과를 확인하고 필요하면 재계획한다`
  - 화면 위치: `작업 현황`의 상태·다음 작업 카드, `작업 계획` 하단 `실행 작업` 카드, 왼쪽 사이드바 `실행 기록`
  - 현재 화면에서 보이는 것:
    - State, queue, stop reason, 기준 파일 준비 상태, ops validation, closure 상태를 확인합니다.
    - 정책이 재계획을 허용하면 해당 행동이 다음 작업으로 나타납니다.
  - 사용자가 해야 할 것:
    - 실행 종료 후 갱신된 State를 먼저 읽습니다.
    - 정책이 제안할 때만 재계획하거나 다음 단일 작업을 진행합니다.
  - 사용자 메모:
    -

- `9. 막힌 작업을 복구하거나 하루를 마감한다`
  - 화면 위치: 왼쪽 사이드바 `복구 센터 · 마감 확인`
  - 현재 화면에서 보이는 것:
    - 무엇이 발생했는지, 무엇이 보존되는지, 지금 허용된 행동이 무엇인지 stop reason별로 분리해 보여 줍니다.
    - 마감 전에는 기준 파일·검증·활성 작업·resume·lock·저장소 상태를 확인합니다.
  - 사용자가 해야 할 것:
    - 막힘 사유를 확인하고 복구 가능한 행동만 실행합니다.
    - 마감은 실행 성공과 별도의 검증 절차로 진행합니다.
  - 사용자 메모:
    -

## 화면 전반 UX 메모

- `버튼 상태와 상호작용`
  - 화면 위치: 모든 버튼. 우선 점검 대상은 `진단 후 등록`, `요구사항 작성`, `요구사항 저장`, `환경 점검 실행`, `실행 작업`, `작업 준비`, `계획 생성`, `재계획`, `마감 검증`입니다.
  - 원하는 공통 동작:
    - 클릭 가능한 버튼은 hover 시 포인터와 색상 변화가 보입니다.
    - 클릭 뒤에는 해당 버튼 또는 인접 영역에 진행 중 표시가 나타납니다.
    - 처리 중에는 같은 작업을 중복 실행할 수 없습니다.
    - 완료 뒤에는 성공·실패·시각·요약·다음 행동이 남습니다.
  - 사용자 메모:
    -

- `용어와 문장`
  - 화면 위치: 사이드바, 카드 제목, 버튼, 오류·안내 문구 전체
  - 현재 기준 용어:
    - `작업공간 연결` 대신 `프로젝트 연결`
    - `오늘 현황` 대신 `작업 현황`
    - `오늘 할 일` 대신 `작업 계획`
    - `다음 행동` 대신 `다음 작업`
    - `요청 작성` 대신 `요구사항 작성`
    - `Doctor` 대신 `환경 점검`
  - 사용자 메모:

- `한글·영문 글꼴과 정보 밀도`

## 2026-07-28 추가 사용자 QA 기록 — Phase 8 입력

- `등록 피드백`
  - 기본 개발용 내장 SDK 경로에서 `진단 후 등록`을 눌러도 아무 반응이 없어 어떤 문제인지 알 수 없습니다.
  - `고급 설정`을 열고 외부 Kit을 명시적으로 연결하면 등록할 수 있습니다.
  - 요구: 기본 경로 실패도 modal 안에서 즉시 원인과 다음 행동을 보여야 합니다.

- `오늘 계획과 과거 내용`
  - 오늘 계획이 없으면 오늘 화면은 공란 또는 오늘 시작 안내여야 합니다.
  - 과거 전략을 보여 줄 때는 현재 계획과 구분된 요약·날짜가 필요합니다.
  - 과거 내용과 개발 전략 원문이 영어인 경우, 정적 제목·상태는 한국어로 이해할 수 있어야 합니다.

- `상태 피드백`
  - 성공·실패에 따라 작은 pop-up 또는 우측 상단 알림 아이콘과 자동 사라지는 slide 카드가 필요합니다.
  - 버튼 hover, pointer, 색상 변화, 클릭 뒤 running 표시가 일관되어야 합니다.

- `상단 상태와 technical 패널`
  - Kit이 등록돼도 `엔진 오프라인`, `프로필 기본`, 녹색 `점검 대기`가 함께 보이면 의미와 상태가 모순되어 보입니다.
  - `READ-ONLY 앱이 소유하지 않음` navigation 문구는 불필요해 보입니다.
  - `META`, `환경` 패널은 의미가 불분명합니다.
  - `아티팩트`와 `ARTIFACTS`가 중복되므로 compact technical 패널은 영문 title을 포함한 하나의 규칙으로 통일합니다.

- `프로젝트 연결`
  - 미설정 경로를 어떻게 해소해야 하는지 화면에서 알 수 있어야 합니다.
  - 앱 UI를 `ko`와 `en` 사이에서 전환할 수 있어야 합니다.
  - 실행 작업의 영문 오류와 `작업 기준 점검`·`환경 점검` 같은 용어는 목적이 드러나는 한국어 설명이 필요합니다.

- `작업 날짜`
  - 날짜를 무한 목록으로 나열하지 않고 한 번에 5개씩 보며 이동할 수 있어야 합니다.
  - 현재 `선택됨` 상태는 더 높은 대비와 명확한 표현이 필요합니다.

- `작업 계획과 요구사항`
  - 개발 전략 Markdown은 읽기 좋은 문서로 렌더링돼야 합니다.
  - `요구사항 작성`은 더 눈에 띄고, 파일명보다 무엇을 입력할지 안내해야 합니다.
  - 사용자가 찾을 수 있는 위치에 `오늘 작업 시작`과 이후 `작업 실행` CTA가 있어야 합니다.

- `글꼴·중복 문구`
  - 영문 글꼴은 자연스럽고 널리 쓰이는 Windows 우선 sans-serif로 보이게 합니다.
  - 같은 내용을 반복하는 heading, badge, helper text는 하나로 통일합니다.
